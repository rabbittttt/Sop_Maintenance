## 二、高危问题

### H1. 审计身份可被伪造：IIS 注入的可信 Windows 身份被后端完全忽略

**证据链**：

- IIS 身份桥接模块在 Windows 认证后注入可信身份：`integration/iis/SopIdentityBridge.cs:100` 写入 `X-SOP-User: b64:<Windows账号>`，并剥离客户端伪造的同名头（第 35 行）。
- 但后端从不读取该头。`server.py:243-244`：
  ```python
  self.identity = frame_identity(self.headers)      # 只解析 Sop-Frame-Identity
  self.actor = self.identity.get("account") or (None if gateway else console_user)
  ```
  `sop/gateway.py:144-161` 的 `frame_identity` 同样只看 `Sop-Frame-Identity`，而这个头来自**浏览器**，任何部门成员都可以用开发者工具把它改成任意账号。
- 审计日志（`server.py:129`）与业务留痕（`events.owner`、`plans.owner`，经 `sop/gateway.py:164-170` 的 `attributed_body` 覆写）全部使用这个可伪造的 `actor`。也就是说：**以他人账号名义保存计划、导入 Excel，留痕完全可信地指向被冒用的人**。
- `PORTAL-INTEGRATION.md:15` 宣称"服务端覆盖客户端自报的维护人，导入同样记录可信操作人"——实际只是把请求体里的 `owner` 字段替换成客户端声明的账号，账号本身仍是客户端声明，与文档表述不符。

**影响**：冒用需要能访问门户（IIS 之后），不是外部攻击面；但内部人员的操作留痕（`sop_audit` 日志、`events` 表、对账 `owner`）可以被随意嫁祸，审计链失效。`roleCode/roleName` 也同样来自客户端（按 AGENTS.md 的约定角色不用于鉴权，此处仅影响展示）。

**建议**（任选其一并保持口径一致）：
1. 网关模式下以 IIS 注入的 `X-SOP-User`（解 base64 后）作为审计主体，`Sop-Frame-Identity` 仅用于会话/展示；两者同时记录进 `sop_audit` 日志便于比对；
2. 或者明确接受"身份由外层 iframe 声明"的模型，修改 `PORTAL-INTEGRATION.md` 的表述，并在 IIS 桥接里删掉死代码 `X-SOP-User` 注入（`SopIdentityBridge.cs:100`），避免给后来者"后端已经校验过身份"的错误安全感。

### H2. 不可变数据表没有任何保留/清理策略，数据库与 WAL 无限增长

**证据**：全库检索确认除 `plan_model_import_previews`、`user_views` 外没有任何 `DELETE`/清理/VACUUM 逻辑。以下表只增不减：

| 表 | 写入频率 | 单行体积 |
| --- | --- | --- |
| `events` | 每次保存 1 行（before+after JSON 都在 `after_json`） | KB 级 |
| `sales_versions` | 每次销量变化 1 行 | 全量销量 JSON（当前约 400 KB） |
| `catalog_versions` | 每次目录变化 1 行 | 全量目录 JSON |
| `snapshots` | 每天至少 1 行 + 手动快照 | 全量 payload（含销量+计划） |
| `workbook_exports` | 每次维护表导出 1 行（含不可变触发器禁止删除） | 完整布局+基准 JSON |
| `plan_download_exports` | **每次网页导出下载 1 行** | 完整快照+manifest+单元格快照 |
| `grid_batch_requests` | 每次网页批量保存 1 行 | 完整保存结果 JSON |
| `demand_import_requests` / `demand_export_baselines` / `plan_import_confirmations` / `plan_download_entry_imports` | 每次导入/导出 1 行 | 不等 |
| `reconcile_sources` | 每份对账资料 1 行 | `raw_text` ≤200 KB + **`content` BLOB ≤15 MB**（截图/Excel 原件永久入库） |

当前库已达 **32 MB + 4.6 MB WAL**，其中对账功能尚未重度使用；每份 15 MB 的截图证据入库后永久保留，长期使用（每天多次导出下载 + 对账资料）将以数百 MB/年速度增长。

放大因素：每日快照 `_snapshot()`（`sop/store.py:1333-1337`）通过 `SELECT * FROM events WHERE recorded_at <= ?` **全量回放自服务启动以来的所有事件**重建状态，事件表越大每个每日快照越慢；`ensure_daily_snapshots` 在每次保存和每次 `/api/state` 轮询都会触发（`store.py:839`、`server.py:718`）。二者叠加意味着服务随运行时间线性变慢。

**建议**：
1. 为"可再生的过程数据"设保留期：`plan_download_exports`（旧下载令牌超过 N 天后其 Excel 本就无法通过基准校验，可以过期）、`plan_import_confirmations`、`grid_batch_requests`、`demand_import_requests`、`workbook_imports`；
2. 对账原始文件（`reconcile_sources.content` BLOB）改为落盘到数据目录（`reconcile_files/`），库内存路径——证据保留不变，库体量受控；
3. `events`/`sales_versions` 等真正的审计表保留，但把每日快照的重建改为增量（记录上次 `history_event_id` 即可，meta 里已有该字段）或定期物化；
4. 运维手册加入定期 `PRAGMA optimize` / 备份后 `VACUUM` 流程。

## 三、中危问题

### M1. 测试基线已红：454 个测试 4 个失败，其中 3 个为确定性失败

完整套件（`python -m unittest discover -s tests`）两次运行结果为 3 失败+1 错误、4 失败，失败集合不稳定。逐一复跑定位：

1. **`test_sales_data.SalesMetricSafetyTests.test_model_lock_confirmation_persists_across_ordinary_refreshes`——确定性失败（陈旧测试）**
   测试把 `source_settings.json` 写到 `<临时根>/data/`（`tests/test_sales_data.py:109-111`），但数据目录集中化之后 `persistent_directory()`（`sop/paths.py:65-72`）在未设 `PLANHUB_DATA_ROOT` 时解析到 `<临时根>/../工作台数据/database/sop`，配置永远不会被读到，锁单口径回落默认值 `source_version_quantity` ≠ 期望的 `model_lock_row`。这是 README「持久目录统一为同级工作区」迁移的遗留，测试仍按旧目录布局写 fixture。
2. **`test_workbench_launcher.WorkbenchLauncherTest.test_close_console_releases_service_and_keeps_saved_plan`——确定性失败（同族陈旧测试）**
   测试在一次性工作区的 `<root>/data/sales.json` 预置产品 `launcher-test`（`tests/test_workbench_launcher.py:54-57`），但被拉起的服务按现行 `persistent_directory` 解析数据目录，读不到这个文件 → 目录为空 → 保存计划时 400「存在无法识别的产品」。
3. **`test_catalog_api.CatalogAPITest.test_rejected_refresh_preserves_published_source`——确定性失败（陈旧测试）**
   `POST /api/refresh` 的 `force=True` 只绕过 5 分钟节流、**不绕过"来源稳定 1 分钟"窗口**（`sop/refresh.py:91-116`）：首次强制轮询必然返回 `waiting`（HTTP 200），而测试期待刷新被尝试后返回 400。现行为与 README「手动点击刷新销量文件……同样等待稳定1分钟」一致，是测试过时。
4. **`test_export_workbook.ExportWorkbookTest.test_artifact_recalculation_and_reference_render`——环境失败**
   Node + `@oai/artifact-tool` 的 WASM 加载崩溃（退出码 0xC0000409，"MONO_WASM: WebAssembly resource does not have the expected content type"）。生产路径会自动回退 Python 生成器（`sop/export.py:124-147`），功能不中断，但说明本机 Node Excel 生成主路径已静默降级。

**影响**：README 承诺的验证入口（`unittest discover`）当前不可作为合并门槛——真回归会被淹没在已知失败里。前两个失败还连带说明：**独立/测试部署把 fixture 放在 `<root>/data` 的旧习惯已经失效**，值得在迁移文档中显式提醒。

**建议**：修前三个测试（fixture 改写到集中数据目录；refresh 测试等待稳定窗口或注入 `clock` 加速）；launcher 测试在 `wait_ready` 后轮询 `/api/state` 直到产品出现；Node 写入器加启动期健康自检并在状态接口暴露降级标志。

### M2. `/api/demand/export` 没有单元格数量上限，可在服务进程内构造百万级工作簿

`sop/demand.py:162-268`：`models` 允许 ≤15000 行、`months` 允许 ≤120 列（再加年合计列），理论上一次请求可让 openpyxl 在**单进程服务内**构建约 360 万单元格的工作簿——内存暴涨、请求长时间占用 `store.lock` 之后的构建时间，拖垮所有其他用户的轮询。对比 SOP 导出接口有 `MAX_QUANTITY_CELLS = 300_000` 的硬上限（`sop/export.py:27, 80-81`），要货导出没有对齐。

**建议**：为 `demand.export_content` 增加与 `export.py` 同级的单元格上限校验。

### M3. HTTP 层没有并发/读超时上限，慢速客户端可占用无上限线程

`ThreadingHTTPServer` 每连接一线程且无上限；`_body`（`server.py:281-298`)按声明的 `Content-Length` 一次性阻塞读取，客户端缓慢发送即可长时间占住线程；`daily_worker`/`backup_worker` 与请求线程共享 `store.lock`，锁被占住时所有 `/api/state` 轮询排队。缓解因素：服务只绑回环、门户模式经 IIS 且 IIS 可配超时，实际暴露面有限，故列为中危加固项。

**建议**：给 socket 设置读超时（`BaseHTTPRequestHandler.timeout`），可选加上限连接数或信号量。

## 四、低危问题与加固建议

- **L1 `runtime_data_directory(root)` 的语义陷阱**（`sop/paths.py:43-44`）：设置了 `SOP_DATA_DIR` 时完全忽略 `root` 参数。本次两个测试失败都与此相关；建议在函数 docstring 里写明，或让测试显式 `patch.dict(os.environ)`。
- **L2 `/api/history` 不分实体**（`sop/store.py:1278-1296`）：plan/shipment/demand 事件混在一起返回（上限 2000 行），前端自行过滤 `entity==='plan'`（`web/app.js:1096`）；shipments 事件多时会挤出 plan 记录。建议支持 `entity` 查询参数。
- **L3 每次 `/api/state` 轮询都开写事务**（`sop/store.py:606`、`823-832`）：`_sync_catalog` 无条件 `BEGIN IMMEDIATE`，即使无任何变化也提交，多人 15 秒轮询下 WAL 持续膨胀（已观测 4.6 MB）。建议先读 digest，无变化跳过写事务。
- **L4 生产持久目录混入测试/预览产物**：`../工作台数据/database/sop/` 下与生产 `sop.sqlite3`、`backups/` 并存着 `test-preview/`（含独立 sqlite、pid、日志）、`test-workbook/` 及十余张预览 PNG。门户预览默认复用生产数据根的设计（`PORTAL-INTEGRATION.md:17`）放大了误备份/误迁移/误删风险。建议预览与测试固定使用独立的 `PLANHUB_DATA_ROOT`，并清理现存产物。
- **L5 浏览器端解析不可信 Excel 的供应链跟进**：对账截图/Excel 在浏览器用 vendored SheetJS 0.20.3（`web/reconcile_ingest/vendor/xlsx.full.min.js`，931 KB）与 Tesseract 离线解析。设计上服务端不解析原始文件、只存 BLOB 作证据（好），但 SheetJS CE 历史上有解析类 CVE，建议建立 vendored 组件的版本登记与升级检查（licenses.html 已附，值得肯定）。
- **L6 覆盖度局限声明**：`sop/xlsx_*.py`（离线 Excel 生成器）与 `scripts/*.mjs`（Node 渲染器）本次为结构化抽扫而非逐行审计；`tests/frontend_*.mjs` 套件未执行（需 Node 前端测试环境）。后续专项审计建议覆盖这两块。

## 五、正面观察（值得保持的设计）

1. **不可变审计与乐观并发**：`events`/`snapshots`/`catalog_versions` 等全部有 `no_update/no_delete` 触发器（`sop/store.py:181-219`）；所有保存走 `BEGIN IMMEDIATE` + revision 冲突检测 + `grid_batch_requests` 幂等回执（`sop/grid.py:45-83`），多人并发语义严谨。
2. **Excel 往返的基线台账**：导出令牌不可变、导入逐单元格三方合并（导出基准/表格值/数据库值），隐藏 `_sync`/`_meta` 页防篡改，行身份用稳定 ID 而非显示名（`sop/workbook.py:476-575`、`sop/roundtrip.py`）。
3. **上传防御纵深**：ZIP 条目数/解压总量/单文件上限、拒绝 DOCTYPE/ENTITY、按 XML 实际坐标校验行列、单元格上限、拒绝公式与日期类型数量（`sop/roundtrip.py:87-137`、`sop/table.py:13-54` 的浮点邻界噪声只容忍单步 ulp）。
4. **网关校验链**：回环限制、代理密钥 `hmac.compare_digest`、Host/Origin 白名单、拒绝 Transfer-Encoding 与重复头、路径拒绝编码分隔符与 `..`（`sop/gateway.py:97-141`）；IIS 桥剥离客户端伪造头、错误信息不泄路径。
5. **单写者启动设计**：先绑端口（`SO_EXCLUSIVEADDRUSE`）再触碰数据，旧隐藏服务接管前核对进程身份/启动时间/命令行/监听归属（`server.py:57-79`、`start-sop.ps1:78-106`）。
6. **前端 XSS 纪律**：app.js/reconcile.mjs 全量使用 `esc()`/`textContent`，未见未转义插入；CSV 导出有公式注入防护（`web/app.js:1101-1105`）。
7. **原子文件发布**：销量/维护表/快照 Excel 全部走临时文件 + `os.replace`，刷新带指纹稳定窗与失败回滚（`sop/refresh.py:53-89`）。
8. **Git 卫生**：跟踪文件中无业务数据/密钥/构建产物，`.gitignore` 覆盖全面（含 `*.pre-central-*/` 迁移备份），`scripts/build_release.py` 的发布校验（reparse point 拒绝、SHA256 逐文件复核、必需文件清单）质量很高。

## 八、复核与处理

- **H1 账号署名**：门户传入的三字段用于业务署名，服务端无法据此证明操作者的身份。这是项目已接受的风险，已修正接入文档的描述。
- **H2、L3 历史与轮询**：历史留存会占用磁盘。已有日快照会按键跳过，重建缺失快照时仍需查询截止时间前的事件。已改为按业务键提取最后一条记录，保留原有截止口径。一次 WAL 大小观测不足以证明持续增长；直接按销量摘要跳过目录同步还可能遗漏人工车型绑定。保留历史、附件和旧导出基线，避免影响追溯和回导。
- **M1、L1、L6 测试**：修正三个失效用例的目录隔离和文件稳定窗口。Windows 启动器、Excel 重算与渲染用例以及前端测试已通过。此次未复现报告中的 WASM 失败。
- **M2、M3 资源限制**：要货计划导出复用现有的 30 万数量格上限，包含年度合计列，在创建工作簿前拒绝超限请求。HTTP 请求增加 60 秒套接字空闲超时，短读会被拒绝；此超时不代表总处理时限或并发上限。
- **L2 修改记录**：计划明细在数据库中先筛选实体，再取最近 2000 条，旧接口仍支持查询全部类型。
- **数据刷新补充**：首次发布销量缓存后若登记失败，原本会留下新文件。已修正并补测有旧文件和无旧文件两个分支。
- **L4、L5 运维项**：本次只隔离测试目录。存量预览文件需由数据负责人确认归属后清理；依赖版本跟进列为维护事项，报告未提供当前版本受影响的具体证据。
